## 1. 김민수·안창선(2025)의 시간 처리 방식을 이렇게 옮겼다

| 논문 (차량, Radar/V2X) | 본 연구 (드론, Camera/LRF/IMU) |
|---|---|
| 기준 시계 = ego 차량 | 기준 시계 = **IMU** |
| Radar 지연 τ₁ = 0.06 s, V2V 지연 τ₂ = 0.12 s (GPS timestamp로 평균값 측정) | 카메라-IMU 시간차 = Kalibr `timeshift_cam_imu`, LRF 지연 `lrf_delay`, OF 처리지연 `proc_latency` |
| 식 (10): `z_true(t − τ) = z_meas(t)` | `t_valid = t_stamp − τ`(LRF), `t = t_cam + shift`(카메라) |
| Fig. 3: V1 GPS를 V2 시각에 **보간**해 동기화 | 자이로(200 Hz)를 영상 구간 [t_{k−1}, t_k]에서 **적분**하고, LRF(30 Hz)는 영상 중간 시각에 **보간** |
| Fig. 4: 늦게 온 측정 → 그 시점으로 돌아가 보정한 뒤 현재까지 **재추정** | `run_filter.m`: 스텝마다 상태를 버퍼에 저장하고, 측정이 `t_avail`에 도착하면 `t_valid` 스텝으로 돌아가 다시 예측·보정 |
| II.G: 4가지 측정 조합(둘 다 / Radar만 / V2V만 / 없음)에 따라 h, R 전환 | 측정모드 1~4 (OF+LRF / OF만 / LRF만 / 없음) |
| 지연 보정 유무로 성능 비교 | 방법 C vs C0 (지연 보정 없음) |

참고: 논문은 측정식의 특이점(`atan(y/x)`) 때문에 UKF를 썼다. 우리 측정식(`v_B = Rᵀv`, `d = p_z/cosθ`)은 특이점이 없으므로 **EKF로 충분**하다. EKF를 쓰면 기본 KF에서 바로 확장할 수 있어 이해하기도 쉽다.

## 2. INSANE 데이터셋 — 실제 데이터를 쓸 때 확인할 것

- nav camera: IDS UI-3270LE, 2056×1542 @ 20 Hz, global shutter, 하향. timestamp는 카메라 내부 시계 기준이고 시작할 때 host와 동기화된다.
- LRF: Garmin Lidar Lite v3, 30 Hz, 1 cm 해상도(σ ≈ 2.5 cm). nav camera와 같은 방향으로 붙어 있다. 25~30 m 이상에서 가끔 **0 값**을 내므로 걸러야 한다(`lrf_min`).
- IMU: PX4 ICM20689 @ 200 Hz (main IMU). 모든 보정값은 PX4 IMU 기준으로 제공된다.
- 정답: 실내 `ground_truth.csv`(OptiTrack), 실외 `ground_truth_8hz.csv` / `ground_truth_80hz.csv`(RTK + 자력계).
- 센서끼리 **하드웨어 동기화가 되어 있지 않다** → 위의 시간 처리가 꼭 필요하다.
- 논문의 VIO 예시(OpenVINS = MSCKF)에서는 이륙할 때 프로펠러 그림자와 특징점이 적은 지면 때문에 추적이 어려웠다. 우리 품질 지표 Q로 확인할 만한 구간이다.

## 3. MSCKF와의 관계 (발표 질문 대비)

- MSCKF: 특징점 하나를 여러 카메라 자세에서 본 **기하 제약**을 측정으로 쓴다. 좌측 영공간에 투영해 특징점 위치를 상태에서 없애므로 계산량이 특징점 수에 선형이다.
- 본 연구: 연속 두 영상의 flow만 쓰고, **LRF로 스케일**을 정해 속도를 측정으로 쓴다(loosely coupled). 구조가 단순하고 하향 카메라와 평지 조건에서 잘 맞는다. 다만 위치와 yaw는 직접 관측되지 않아 느리게 드리프트한다. VIO에서도 위치 3개와 yaw 1개는 관측 불가능하다.
