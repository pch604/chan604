# v6 — 시각 요소의 근거와 구현·데이터·평가 계획

## 1. 시각 요소별 근거

v5에서 근거 없이 만든 요소(≈ 25 cm 카드, 둥근 일정 막대)를 없앴습니다. 나머지 요소는 실제 논문·오픈소스·기업 문서가 같은 내용을 표현하는 방식을 찾아 그에 맞췄습니다.

| 슬라이드 | v5 (근거 약함) | v6 | 근거 |
|---|---|---|---|
| 필요성 | "5 m/s × 50 ms ≈ 25 cm" 계산 카드 | **실제 비행제어기 지연 설정값**: PX4 EKF2 기본값 Optical Flow 7 ms · 거리센서 5 ms, 센서별 최대 300 ms | PX4-Autopilot 소스 `params_optical_flow.yaml`, `params_range_finder.yaml` (직접 확인). 7 ms는 DroneCAN flow 노드에서 프레임이 비행제어기에 도착하기까지의 시간에 맞춘 값 |
| 필요성 | 시점 차이 설명만 있음 | "타임스탬프와 실제 측정 시점의 차이는 융합 성능을 크게 저하" 문장에 인용 | Qin & Shen, IROS 2018 (Best Student Paper). Fig. 1이 카메라·IMU의 샘플링 시점 vs 타임스탬프 시점을 두 줄로 비교하는 방식 |
| 연구방법 | 시간 처리 ①②③에 출처 없음 | "참고한 처리 구조" 박스 추가 | MSF-EKF (Lynen et al., IROS 2013): 지연 측정이 오면 과거 상태에서 다시 예측하고 이후 측정을 재적용. PX4 EKF2: 센서별 FIFO 버퍼 + 지연을 반영한 fusion time horizon + output predictor |
| 연구방법 | 센서 → EKF → 결과 블록 | 유지 | 다중센서 EKF를 입력 → 필터 → 상태로 그리는 일반 형식(MSF-EKF, PX4 EKF2 문서와 같은 구성) |
| 구현·평가 (신규) | — | ATE · RE, 위치+yaw 4자유도 정렬 | Zhang & Scaramuzza, IROS 2018 (VO/VIO 궤적 평가 튜토리얼). MATLAB에도 `compareTrajectories`(R2024b, ATE/RE)가 있음 |
| 구현·평가 (신규) | — | 데이터 사양(카메라 20 Hz, 거리계 30 Hz, CSV+PNG, OptiTrack 정답) | INSANE 논문(Brommer et al., IJRR 2024)과 공식 데이터셋 페이지 |
| 연구계획 | 둥근 막대, 칸 경계와 안 맞음 | **균일 시간축(반월 단위) + 칸 경계에 맞춘 직사각형 막대 + 세로 격자선** | 일반적인 Gantt 차트 형식(막대 길이 = 기간, 균일한 시간축) |
| 배경 · 선행연구 · 참고문헌 | 연구실 참고 PPT 형식 | 유지 | 같은 연구실(VDEC) 학생자율연구 발표 PPT 형식 |

참고문헌은 9편으로 늘었습니다(Qin & Shen 2018, Lynen 2013, Zhang & Scaramuzza 2018, Brommer 2024 추가).

## 2. Python + MATLAB 병행 — 추천: 그렇게 하세요

**역할 분담**

| 단계 | 도구 | 이유 |
|---|---|---|
| 영상 처리 (특징점·KLT) | **Python + OpenCV** (`goodFeaturesToTrack` = Shi–Tomasi, `calcOpticalFlowPyrLK` = KLT) | 무료이고 예제가 가장 많습니다. 3 MP 영상을 빠르게 처리할 수 있고, 프레임별 처리시간을 바로 잴 수 있습니다 |
| 필터 모델·시간 처리 | **MATLAB** | 행렬·야코비안 유도와 디버깅이 편합니다. 연구실(VDEC)이 MATLAB/Simulink를 주로 쓰므로 교수님 피드백을 받기 쉽습니다 |
| 평가·그래프 | MATLAB (`compareTrajectories`, R2024b 이상) 또는 Python `evo` | 둘 다 ATE/RE를 지원합니다. MATLAB 버전이 낮으면 직접 계산하거나 evo를 쓰면 됩니다 |

**두 언어를 이어 주는 규칙** (병행할 때 가장 흔한 실수 방지)
- Python 출력은 CSV 하나로 고정합니다: `t_meas, t_proc, du, dv, n_features, track_ratio, residual`
- 시간은 모두 **초(s), float64, 데이터셋과 같은 시계**를 씁니다.
- MATLAB은 이 CSV와 데이터셋의 IMU·거리계 CSV만 읽습니다.

**대안:** MATLAB만으로도 가능합니다(Computer Vision Toolbox의 `vision.PointTracker`가 KLT). 라이선스와 속도를 확인해 보고, 문제가 있으면 바꿔도 연구 내용은 그대로입니다.

## 3. 데이터·진행·평가 계획 (질의응답 대비 상세판)

### 데이터: INSANE (Brommer et al., IJRR 2024)
- **센서:**
  - 하향 내비게이션 카메라(그레이, 2056×1542, 20 Hz, 글로벌 셔터)
  - 같은 방향으로 장착된 레이저 거리계(Garmin Lidar-Lite v3, 30 Hz)
  - IMU 여러 개(200 Hz 이상)
- **형식:** CSV(헤더 포함) + PNG 영상 + 타임스탬프 CSV, 보정값은 YAML입니다. ROS 없이 Python·MATLAB에서 바로 읽을 수 있습니다.
- **정답:** 실내는 OptiTrack 모션캡처, 실외는 dual RTK-GNSS입니다. 이 연구는 **실내 구간 + OptiTrack 정답**을 사용합니다.
- **카메라 타임스탬프:** 카메라 내부 시계 기준이라 **실제 촬영 시점**을 나타냅니다. 센서 간 동기는 소프트웨어 방식이며 정확도는 약 100 µs입니다.

### 핵심 설계 포인트: 지연을 어떻게 만들 것인가
데이터셋의 타임스탬프는 이미 "측정 시점"입니다. 그래서 실제 시스템에서 생기는 **도착 지연은 따로 만들어 줘야** 합니다.

- **도착 시점** = 측정 시점 + (Python에서 실측한 영상 처리시간) + (추가 지연 0·25·50·100 ms)
- 추가 지연 범위는 PX4 EKF2가 허용하는 0~300 ms 범위 안에서 잡았습니다.

교수님 질문 가능성이 높은 부분이니 이 설명을 꼭 준비하세요.

### 진행 순서
1. **10월 전반:** 데이터 다운로드, 센서별 주기·타임스탬프 확인, 실내 시퀀스 선정
2. **10월 후반:** Python KLT로 영상 이동 CSV 생성 → MATLAB EKF로 지연 없이 기본 융합(기준 결과 확보)
3. **11월:** 버퍼(과거 상태·IMU 입력·측정값) + 측정 시점 보정 + 현재까지 재추정 구현
4. **12월:** 조건 A/B × 지연 4단계 비교, 오차와 처리시간 분석, 보고서 작성

### 평가
- **비교 조건:**
  - A. 지연 무시: 도착한 측정을 현재 값으로 바로 보정
  - B. 시간 처리: 측정 시점 보정 후 재추정
- **지표:**
  - ATE(위치 RMSE, 위치+yaw 4자유도 정렬)
  - RE(이동 구간 길이별 상대 오차)
  - 처리시간(재추정 비용)
- **기대 그림:**
  - 지연이 커질수록 A의 오차가 증가하는지
  - B가 그 증가를 얼마나 줄이는지
  - B의 처리시간이 얼마나 늘어나는지

## 4. 발표 전에 직접 확인할 것

1. INSANE 실내 시퀀스 이름과 OptiTrack 구간을 실제 다운로드 후 확인하세요. 공개 요약으로만 확인한 상태입니다.
2. 사용할 IMU를 정하세요. 여러 개가 있으니 거리계·카메라와 같은 모듈의 것을 우선 검토하세요.
3. MATLAB 버전이 R2024b 이상인지 확인하세요(`compareTrajectories`). 아니면 evo를 쓰면 됩니다.
4. 3 MP 영상의 KLT 처리시간이 너무 길면 해상도를 줄이세요. 줄인 비율도 처리시간과 함께 기록합니다.
5. MS PGothic에는 한글 글자가 없어 PowerPoint가 대체 글꼴로 표시합니다. 발표용 PC에서 줄바꿈을 확인하세요.

## 5. 발표 시간
